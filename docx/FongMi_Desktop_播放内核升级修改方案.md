# FongMi Desktop 播放内核升级修改方案

> 文档状态：实施版
> 当前阶段：更新为一次性目标架构，并同步进行代码实现
> 适用工程：FongMi Desktop
> 目标平台：macOS、Windows、Linux
> 核心结论：不再按四个产品阶段渐进改造，而是一次性建设“统一播放器 + 播放决策层 + 应用内高兼容播放内核”。Web 播放器继续承担标准播放，高兼容播放由 native-libmpv 承担；用户播放失败时只在应用内执行换线路、换来源或重试。

---

## 1. 背景说明

当前产品已经具备较完整的播放链路：

- 通过播放源解析获得播放地址；
- 通过媒体探测和嗅探处理直链、网页地址、Header、字幕、弹幕等信息；
- Web 播放侧已经引入 ArtPlayer、HLS.js、原生 HTML Video 等能力；
- 兼容播放侧已经存在 MPV 控制能力，并通过 MPV 处理 Web 播放器无法播放的复杂媒体源；
- 播放失败后可以触发兼容播放器 fallback。

但当前问题在于：

> 当 ArtPlayer 或 Web 播放器无法播放时，需要调用 MPV 播放器进行播放，播放体验与主应用割裂，用户会明显感知到“跳出了当前软件”。

这会带来几个体验问题：

1. 播放窗口和主应用窗口分离，用户体验不连续；
2. 选集、播放进度、倍速、暂停、下一集等控制无法保持统一；
3. 用户会看到 ArtPlayer、MPV 等技术概念，产品表达不够自然；
4. 一旦外部播放器未安装、路径异常或平台差异明显，容易出现不可控问题；
5. 跨平台发布时，Windows、macOS、Linux 的外部播放器依赖会进一步放大维护成本。

因此，本次修改方案重点不是简单替换 Web 播放器，而是重新定义播放体系：

> 用户看到的是一个统一播放器；底层根据媒体源情况自动选择标准播放内核或高兼容播放内核。

---

## 2. 目标与非目标

### 2.1 修改目标

本次播放内核升级的目标包括：

1. 解决 ArtPlayer / Web 播放器无法播放时体验割裂的问题；
2. 将 MPV 从“外部兜底播放器”升级为“应用内高兼容播放内核”；
3. 保持播放页、选集、进度、历史、倍速、字幕、弹幕、错误提示等体验统一；
4. 建立播放决策层，自动选择标准播放或高兼容播放；
5. 为后续 macOS、Windows、Linux 三端统一播放体验打基础；
6. 降低用户对技术实现的感知，避免出现“ArtPlayer 播放失败，请打开 MPV”这类工程化表达。

### 2.2 非目标

本次方案不建议立即做以下事情：

1. 不建议立即将 ArtPlayer 替换为 xgplayer；
2. 不建议把 MPV 继续作为外部播放器长期依赖；
3. 不建议直接重写整个应用界面；
4. 不建议当前阶段直接做完整 Kodi 类媒体中心能力；
5. 不建议完全放弃 Web 播放器，因为 Web 播放器仍适合常规 MP4、HLS、直播和轻量播放场景。

---

## 3. 核心判断

### 3.1 xgplayer 不是根本解法

xgplayer 可以作为 Web 播放器候选，但它和 ArtPlayer 一样，本质仍运行在浏览器 / Chromium / MSE 能力范围内。

它可以改善：

- Web 播放器 UI；
- HLS、FLV、DASH 等格式的插件化处理；
- 直播、点播和 Web 控件体验；
- Web 播放层的工程封装。

但它不能根治：

- Chromium 不支持的编码；
- HEVC、AC3、DTS 等复杂音视频编码；
- MKV、特殊 TS、异常 FLV 等复杂容器；
- 依赖复杂 Header、Cookie、Referer 的源；
- 源站返回非标准媒体流、跳转链、反盗链等问题。

因此，xgplayer 可作为后续 Web 标准播放层候选，但不能作为本次兼容性问题的主方案。

### 3.2 MPV/libmpv 是高兼容播放的关键

类似 Jellyfin Desktop、Plex HTPC、Stremio Desktop、IINA、Celluloid、mpv.net、SMPlayer 等产品，本质上都采用了类似思路：

> UI 和业务体验由应用自己负责，复杂媒体播放能力交给 MPV / libmpv / FFmpeg / libVLC 这类成熟播放内核。

这类产品的共同点是：

- 不让 Web 播放器承担所有播放场景；
- 业务界面与播放内核解耦；
- 播放内核专注兼容性、解码、字幕、音轨、硬解；
- 产品界面专注媒体库、搜索、详情、选集、历史、设置；
- 用户看到的是统一客户端，而不是多个割裂播放器。

当前 FongMi Desktop 的源来自 TVBox / FongMi 生态，播放源格式、编码、Header、跳转链不可控，因此更适合采用类似 Jellyfin / Plex / Stremio 的桌面端方案。

## 4. 一次性目标架构

本次不再按照四个产品阶段交付，而是直接建设目标态播放体系。

```text
FongMi Desktop 统一播放器

播放请求
  ↓
DesktopPlaybackService
  ↓
媒体解析 / 探测 / 嗅探
  ↓
PlaybackSessionStore
  ↓
PlaybackEngineSelector
  ├─ Web 标准播放：ArtPlayer / EmbeddedPlayer / HLS.js
  ├─ 应用内高兼容播放：NativePlayerHost + MPV/libmpv
  └─ 外部播放器兜底：IINA / VLC / System
```

用户体验目标：

> 用户只看到一个播放器。普通源走标准播放，复杂源走高兼容播放，极端情况下才允许用户主动使用外部播放器。

研发实现上仍需要按模块拆分任务，但产品交付形态直接面向最终统一播放器，不再先做过渡版外部 MPV 体验。

## 5. 播放模式设计

### 5.1 面向用户的播放模式

不建议在产品中直接暴露 ArtPlayer、xgplayer、MPV 等技术名称。

建议在设置页和播放页中使用以下产品化命名：

| 用户看到的模式 | 实际含义 | 适用场景 |
|---|---|---|
| 智能播放 | 自动选择标准播放或高兼容播放 | 默认推荐模式 |
| 标准播放 | 使用 Web 播放器，如 ArtPlayer / EmbeddedPlayer | 常规 MP4、HLS、直播源 |
| 高兼容播放 | 使用 MPV/libmpv 播放内核 | 黑屏、无法加载、只有声音、复杂格式、异常线路 |
| 外部播放器 | 调用 IINA / VLC / 系统默认播放器 | 最后兜底，不作为主流程 |

默认建议使用“智能播放”。

### 5.2 播放失败提示

不建议提示：

> ArtPlayer 播放失败，正在调用 MPV 播放器。

建议改为：

> 当前线路兼容性较差，已自动切换高兼容播放模式。

或者：

> 标准播放模式无法正常加载该视频，已切换到高兼容播放模式。

这样用户感知的是“软件自动处理问题”，而不是“技术组件失败”。

## 6. 一次性落地范围

本次改造一次性纳入以下内容：

| 模块 | 建设内容 |
|---|---|
| 播放模式 | 设置页提供“智能播放 / 标准播放 / 高兼容播放” |
| 播放决策层 | 新增 `PlaybackEngineSelector`，在播放前决定使用 Web 或高兼容内核 |
| Web 标准播放层 | 保留 ArtPlayer / EmbeddedPlayer / HLS.js，不在本轮强行切换 xgplayer |
| 高兼容播放层 | 新增 `NativePlayerHost`，用于承载高兼容播放流程 |
| MPV 控制 | 复用现有 MPV JSON IPC，后续平滑替换为 libmpv 深度集成 |
| 播放状态 | 高兼容播放也回传进度、时长、暂停、结束等状态 |
| 播放控制 | 播放、暂停、seek、倍速、音量、静音、上一集、下一集、选集统一在播放页处理 |
| 快捷键 | 高兼容播放页支持空格、方向键、M、PageUp/PageDown、Esc 等常用快捷键 |
| 错误恢复 | 高兼容播放失败时优先展示用户可理解的恢复提示，并支持重新尝试 |
| 外部兜底 | 高兼容播放失败时在统一播放页内触发，不退回旧错误弹窗 |
| 播放历史 | 标准播放和高兼容播放共用播放历史保存逻辑 |
| 外部播放器 | 仅作为极端兜底，入口保留但弱化 |
| 跨平台 | macOS 先闭环，Windows/Linux 按相同架构适配 |

## 7. 当前已实施内容

本次已开始按一次性目标架构进行代码实现，当前已完成以下基础改动：

1. 新增播放模式类型：`auto`、`standard`、`compatibility`；
2. 新增播放决策模块：`src/desktop/player-engine-selector.ts`；
3. `DesktopPlaybackService.prepare` 支持接收 `playbackMode`；
4. 播放引擎选择不再只是简单判断 Web 是否可播，而是由 `PlaybackEngineSelector` 决定；
5. 设置页新增“播放模式”；
6. 播放准备时将当前播放模式传入主进程；
7. 新增 `NativePlayerHost.vue`，用于应用内展示高兼容播放状态和统一控制栏；
8. `PlayerContainer.vue` 根据播放会话的 `engine` 自动切换 Web 播放或高兼容播放；
9. Web 播放失败时不再直接关闭播放页，而是切换到高兼容播放视图；
10. 高兼容播放启动失败时，可以在统一播放页内继续尝试外部播放器兜底；
11. 高兼容播放状态监听已收敛到 `NativePlayerHost`，不再由 App 顶层维护旧的兼容播放上下文；
12. 新增高兼容播放记忆：标准播放失败并切入高兼容后，会记住该线路/剧集，下次智能播放直接优先高兼容；
13. 设置页提供“高兼容播放记忆”数量展示和清除入口，避免历史记忆长期误判；
14. MPV 控制层新增音量、静音状态观察和控制；
15. 高兼容播放页新增音量条、静音按钮和常用播放快捷键；
16. 高兼容播放失败时优先显示 `userMessage`，并提供“重新尝试高兼容播放”；
17. 外部播放器仍保留为最后兜底。

当前实现重点是先打通“一次性目标架构”的入口和状态模型，让用户始终停留在统一播放页内完成标准播放、高兼容播放和外部兜底，并通过播放记忆减少重复失败等待。真正完全内嵌 libmpv 的视频渲染仍需要后续专项完成，专项技术规划详见：`docx/FongMi_Desktop_libmpv原生深度内嵌渲染技术方案.md`。

## 8. 目标技术结构

### 8.1 播放决策层

新增或强化：

```text
src/desktop/player-engine-selector.ts
```

职责：

- 根据媒体格式、URL、Header、用户播放模式选择播放内核；
- 统一输出 `web` 或 `mpv`；
- 替代简单的 `isWebPlaybackCandidate` 判断；
- 避免所有源都先经过 Web 播放器失败后再 fallback。

决策依据包括：

| 判断项 | 建议处理 |
|---|---|
| 播放模式 = 高兼容播放 | 直接使用高兼容播放 |
| 播放模式 = 标准播放 | Web 可播则标准播放，否则高兼容播放 |
| format = hls / mp4 / webm / audio | 优先标准播放 |
| format = flv / dash / mpeg-ts / unknown | 倾向高兼容播放 |
| URL 后缀为 mkv、flv、ts、m2ts、avi、wmv 等 | 倾向高兼容播放 |
| URL 需要 Cookie / Referer / Authorization | 保留受控媒体协议，避免直接暴露给外部播放器 |
| 用户手动选择高兼容播放 | 直接进入高兼容播放 |

### 8.2 播放页组件结构

```text
PlayerContainer
  ├─ Web 标准播放
  │   ├─ ArtPlayerHost
  │   └─ EmbeddedPlayer
  └─ 高兼容播放
      └─ NativePlayerHost
```

上层统一处理：

- 关闭；
- 上一集；
- 下一集；
- 选集；
- 进度上报；
- 播放结束；
- 错误提示；
- 自动 fallback。

### 8.3 播放状态统一

无论底层使用 Web 播放还是 MPV/libmpv，都应向上暴露统一的播放状态模型：

```text
PlaybackState
  ├─ engine: web | mpv | external
  ├─ status: loading | playing | paused | buffering | ended | error
  ├─ position
  ├─ duration
  ├─ speed
  ├─ volume
  ├─ muted
  ├─ subtitleTrack
  ├─ audioTrack
  ├─ errorCode
  └─ errorMessage
```

上层页面只关心统一状态，不直接依赖具体播放器实现。

## 9. 产品交互方案

### 9.1 播放页体验

播放页保持一个完整统一的界面：

```text
┌──────────────────────────────────────────────┐
│ 返回   剧名 / 集数                            │
├──────────────────────────────────────────────┤
│                                              │
│                  视频画面                     │
│                                              │
├──────────────────────────────────────────────┤
│ 播放/暂停  进度条  时间  倍速  选集  设置       │
└──────────────────────────────────────────────┘
```

底层播放内核可以切换，但界面不应明显变化。

### 9.2 自动切换体验

标准播放失败时：

1. 保留当前播放页；
2. 展示短提示；
3. 自动切换高兼容播放；
4. 尽量继承当前播放进度；
5. 切换完成后继续播放。

推荐提示：

> 标准播放模式无法正常加载，已切换到高兼容播放模式。

### 9.3 手动切换入口

播放页设置中可以增加：

- 使用标准播放；
- 使用高兼容播放；
- 当前线路以后优先使用高兼容播放；
- 使用外部播放器打开。

其中“使用外部播放器打开”放在次级位置，不作为主按钮。

### 9.4 设置页调整

建议在设置页中将“应用内播放器”改造成“播放模式”：

| 设置项 | 说明 |
|---|---|
| 智能播放，推荐 | 自动选择标准播放或高兼容播放 |
| 标准播放 | 优先使用 Web 播放器，界面轻量 |
| 高兼容播放 | 优先使用高兼容播放内核，适合复杂线路 |
| 标准播放内核 | 稳定播放器 / ArtPlayer 实验版 |
| 自动切换高兼容播放 | 标准播放失败后自动切换 |
| 外部播放器偏好 | IINA / VLC / 系统默认，仅作为兜底 |

## 11. 跨平台注意事项

### 11.1 macOS

重点关注：

- arm64 / x64 双架构；
- 应用签名与公证；
- libmpv 动态库打包；
- 原生播放窗口与 Electron 主窗口叠加；
- 全屏、多显示器、Retina 缩放；
- IINA 作为外部兜底可选项。

### 11.2 Windows

重点关注：

- mpv.exe / libmpv.dll 分发；
- GPU 硬解差异；
- 窗口句柄绑定；
- 防火墙和安全软件误报；
- 便携版与安装版的资源路径；
- VLC 或系统默认播放器作为外部兜底。

### 11.3 Linux

重点关注：

- AppImage / DEB 依赖；
- libmpv、FFmpeg、VAAPI 依赖差异；
- Wayland / X11 窗口行为差异；
- 不同发行版显卡驱动差异；
- VLC 或系统默认播放器作为外部兜底。

## 12. 风险与控制措施

| 风险 | 影响 | 控制措施 |
|---|---|---|
| 原生播放承载层开发复杂 | 交付周期变长 | 产品目标一步到位，研发模块化实施 |
| 三端窗口行为不一致 | 播放页体验不统一 | macOS 优先验证，再扩展 Windows / Linux |
| 打包体积增加 | 安装包变大 | 高兼容内核按平台拆包，控制资源体积 |
| MPV/libmpv 许可合规 | 发布风险 | 梳理 GPL/LGPL 构建方式和依赖分发策略 |
| 播放崩溃 | 用户体验受损 | 播放内核独立进程隔离，主应用保活 |
| Header / Cookie 传递不安全 | 播放失败或泄露风险 | 保留受控媒体协议，禁止敏感 Header 直接传给外部播放器 |
| 弹幕和字幕覆盖复杂 | 首期体验受限 | 首期先保证播放、控制、进度，弹幕覆盖后续增强 |

## 13. 推荐实施结论

本次播放体验问题不建议通过简单替换 ArtPlayer 为 xgplayer 解决。

更推荐的修改方向是：

> 保留 Web 播放器作为标准播放能力，新增应用内高兼容播放内核，将 MPV/libmpv 从外部兜底升级为应用内播放承载层。

最终产品形态应是：

```text
用户只看到一个播放器
  ├─ 常规源：标准播放模式
  ├─ 复杂源：高兼容播放模式
  └─ 极端情况：外部播放器兜底
```

技术主线建议是：

```text
Electron 业务界面
  +
播放决策层
  +
Web 标准播放内核
  +
应用内高兼容播放承载层 MPV/libmpv
```

一句话总结：
